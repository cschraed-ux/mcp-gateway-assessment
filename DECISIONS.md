| # | Decision | Why |
|---|---|---|
| 1 | **Build all four tasks** of the assessment, each as a standalone, runnable workspace. | You said "build all". |
| 2 | **TypeScript / Node.js** for every task. | Matches the assessment's own examples (`@modelcontextprotocol/sdk`, Zod, Node.js proxies) and keeps one toolchain for graders. |
| 3 | **Code lives in `/Users/chad/Apps/mcp-gateway-assessment`**, a new folder next to your other apps, with its own git repo. | The session had no folder; a take-home should not live in a folder the app deletes with the session. Move it anywhere later. |
| 4 | **npm workspaces monorepo**, but **no shared code between tasks**. | Graders cd into one task; each must stand alone. Workspaces only share `node_modules` and the root `npm run check`. |
| 5 | **No HTTP framework** (Express/Fastify). Built-in `node:http` + global `fetch`. | A proxy assessment is about understanding the wire format and streams; a framework hides exactly what is being graded, and it keeps the dependency tree tiny. |
| 6 | **Zod 4** for Task 1 validation (the SDK supports it natively). | Current major; the SDK 1.32 docs use it. |
| 7 | Task 1 returns **-32602 Invalid params** for schema failures and unknown tools, and **tool-level `isError` results** for business failures such as an unknown customer. To get the real JSON-RPC error, Task 1 **replaces the SDK's `tools/call` handler** with a thin dispatcher that runs the same strict Zod schemas; `registerTool` is still used so `tools/list`, titles, annotations and output schemas come from the SDK. | SDK 1.32.2's built-in handler catches its own `McpError` for bad arguments and returns `{isError:true}` instead (verified in `mcp.js`), which would fail the assessment's "standard JSON-RPC error codes" requirement. |
| 7a | Task 1 policy limits: `CUST-XXXXX` means exactly five digits; `amount` has at most 2 decimals and a maximum of 10,000 by default, overridable with `MAX_REFUND_AMOUNT`; `reason` is trimmed then 10–500 chars. | Money fields need a precision rule; a cap is a sensible refund-tool default and env-configurable so the grader can test it. |
| 8 | Task 2 auth tokens are **HS256 JWTs with a `role` claim**, verified with `node:crypto`, plus an optional static token table for local demos. | Realistic without adding an auth library; the role is cryptographically bound to the token instead of trusted from a header. |
| 9 | Task 2 **forwards unknown methods** (initialize, ping, resources/*) transparently and only intercepts `tools/call`; batches are split so denied calls are answered locally and allowed ones are forwarded. | The statement says forward `tools/list` transparently; an MCP client must also initialize. Per-item batch handling is required for JSON-RPC correctness. |
| 10 | Task 3 uses a **pattern-aware hold-back buffer**: only the trailing characters that could still begin a sensitive pattern are held, capped at a fixed length; everything before is flushed immediately. | Lets patterns split across chunks be caught without buffering the response; TTFT delay is bounded by the cap. |
| 11 | Task 3 ships a **mock streaming provider** for tests and demos, plus adapters for **Anthropic Messages** and **OpenAI-compatible** SSE streams, selected by env var. | Tests must be deterministic and offline; graders may still point it at a real provider. |
| 12 | Task 4 uses **better-sqlite3** (synchronous, WAL mode) rather than Node's built-in `node:sqlite`. | `node:sqlite` still prints an ExperimentalWarning on Node 24 and is absent on Node 20; better-sqlite3 has prebuilt binaries and gives atomic check-and-reserve transactions. |
| 13 | Task 4 rate limiter **reserves an estimated token count at admission** (chars/4 of prompt + requested max_tokens) and **reconciles to actual usage** after the response. | A token-aware limiter cannot know the real count before the call; reserve-then-settle prevents a burst of concurrent requests from all passing the check. |
| 14 | Task 4 standard error payload: `{ "error": { "code", "type", "message", "request_id", "retryable" } }` with HTTP status mapped from `type`. | One shape for every failure, nothing from upstream copied into it. |
| 15 | The finished work is **committed locally** on `main` (one commit) but **not pushed**: there is no remote. | A local commit is reversible and records the reviewed state; pushing needs a GitHub repo you create, which is a held question. |
| 9a | Task 2 pipeline order is route → method → Origin → Content-Type → **auth → body cap → parse**, so an unauthenticated caller never makes the gateway buffer or parse anything. HTTP statuses: -32001 → 403, -32002 (no/invalid token) → 401, parse/invalid request → 400, downstream failure -32003 → 502, downstream answers (including its own JSON-RPC errors) → 200. `tools/call` without a tool name → -32602 with the request id echoed. | Fail closed and cheap to reject; status codes follow the HTTP meaning while the JSON-RPC body carries the precise code. |
| 9b | Task 2 forwards `tools/list` **unchanged** for every role, as the statement says; filtering `admin_*` tools out of a viewer's list is noted in its README as a production improvement, not done. | The statement is explicit; hiding tools is a UX nicety, denial at call time is the security control. |

| 13a | Task 4 failover policy: fail over on upstream **429, timeout, 5xx, 408, 401/403, network errors and malformed responses**; do **not** fail over on other 4xx (400, 404, 413, 422), which become `502 upstream_rejected`. Both timed out → 504; otherwise both failed → 503 retryable. | A backup provider can survive the primary being overloaded, down, slow or mis-credentialed. It cannot fix a request the provider considers invalid, so retrying it would burn latency and budget. |
| 13b | Task 4 checks the tenant API key **before reading or validating the body** (only the declared-size cap runs first), the same order as Task 2, and releases the token reservation when an attempt times out or fails. | An unauthenticated caller learns only "401" and cannot make the gateway buffer anything; charging for timed-out calls is a cost-control trade-off noted in the README's production section. |
| 13c | Task 4 adds `413 request_exceeds_token_limit` for a single request larger than the tenant's whole per-minute budget, instead of returning a `Retry-After` that could never be satisfied. | Correctness of the limiter's "wait" advice. |
| 10a | Task 3 hold-back cap `MAX_HOLD_CHARS` defaults to **320** (RFC-length email), not 64. Headers are committed on the first token or after a 1000 ms grace (`FIRST_BYTE_GRACE_MS`), whichever comes first, so a provider failure before the first byte can still be a clean 502 instead of a 200 that dies mid-stream. On a mid-stream provider error the held tail is discarded, never flushed. | In prose the hold is only the trailing word, so the larger cap costs no latency but closes a truncation gap. A 200 followed by an SSE error is worse for clients than a 502. Held text may be the start of PII. |
| 11a | Task 3 Anthropic adapter uses raw `fetch` (no SDK, no runtime deps), default model `claude-sonnet-5-5`, `anthropic-version` `2023-06-01` (overridable), and the server-side refusal-fallback beta **off** by default. | Zero-dependency rule for Tasks 2 and 3; known-good API version; a beta a grader's account lacks would turn every real call into an error. |
| 11b | Task 3 detectors: SSN only with `-` or space separators (a bare 9-digit number is not an SSN); card numbers 13–19 digits with Luhn validation, trimmed to the longest Luhn-valid prefix; leftmost-longest match wins across detectors. | Avoids redacting order numbers, IDs and phone numbers while catching the real patterns. |
| 10b | Task 3 idle flush (`IDLE_FLUSH_MS`) defaults to **0**, i.e. off: the output is exactly what redacting the full text would give, regardless of chunking. Turning it on (e.g. 250 ms) releases a trailing plain word during an upstream pause and can expose an email's local part before the `@` arrives; the domain is still redacted. | Providers stream continuously, so the liveness gain is one word at most; the security property of exact equivalence is worth more in a guardrail. |
| 10c | Task 3 treats a clean upstream EOF without `[DONE]` or `message_stop` as a normal end of stream (held tail still redacted and flushed). | Strict failure would break lenient OpenAI-compatible servers; nothing can leak either way. |
| 16 | All three HTTP services (Tasks 2, 3, 4) set `server.requestTimeout` 30 s and `server.headersTimeout` 10 s (env-overridable) and bind to `127.0.0.1` by default where demo credentials are seeded (Task 4). | Node's defaults (300 s / 60 s) let a slowly dribbled body hold a connection for minutes; the demo keys are public in the README. |
| 17 | Task 2 rejects a request whose `id` is `null` with -32600. | JSON-RPC tolerates it, MCP forbids it; the gateway follows the stricter MCP rule. |
| 18 | Task 1 adds a stdin guard in front of the SDK transport: unparseable lines → -32700, arrays and bad envelopes → -32600 (id echoed when recoverable), oversized lines discarded and answered -32600. Refund `amount` minimum is 0.01. | The SDK's stdio transport drops malformed lines silently, which violates the "standard JSON-RPC error codes" requirement; amounts below one cent rounded to a zero refund. |
